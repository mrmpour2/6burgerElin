# Table Talk — روایت‌های صفحهٔ اصلی (و نظرهای صفحهٔ محصول)

این سند می‌گوید بخش «Table Talk» چطور کار می‌کند، داده از کجا می‌آید، مدیر چطور
روایت‌ها را انتخاب می‌کند و در هر وضعیت شبکه چه چیزی روی صفحه دیده می‌شود.

## ۱. تصویر کلی

```
وب‌سایت (React)                 بک‌اند Express (dashboard/backend)        دیتابیس
────────────────                ──────────────────────────────────        ────────
TableTalk.tsx
  └─ useTableTalk.ts
       └─ api/testimonials.ts ──► GET /api/public/testimonials ──► reviews (APPROVED + featured)
                                     (بدون توکن، فقط خواندنی)

ReviewsSection.tsx (صفحهٔ محصول)
  └─ api/reviews.ts ────────────► GET  /api/public/reviews?productId=…
                                  POST /api/public/reviews ─────► reviews (PENDING)

پنل ادمین: /comments
  └─ hooks/api/useReviews.js ──► GET    /api/reviews        (توکن ادمین)
                                  PATCH  /api/reviews/:id   (تأیید/رد + Table Talk)
                                  DELETE /api/reviews/:id
```

هر سه مسیر روی **یک جدول** کار می‌کنند: `reviews`. تفاوت فقط در فیلترها و در
دسترسی است.

## ۲. مدل داده (`prisma/schema.prisma` → `model Review`)

| فیلد | توضیح |
| --- | --- |
| `productId` | محصول مرتبط (اختیاری، `onDelete: SetNull`). نظرها روی صفحهٔ محصول با آن فیلتر می‌شوند. |
| `authorName` / `authorNameEn` | نام نمایشی مشتری (فارسی + ترجمهٔ اختیاری انگلیسی). |
| `body` / `bodyEn` | متن روایت (فارسی + ترجمهٔ اختیاری انگلیسی). |
| `rating` | امتیاز ۱ تا ۵ **یا `null`**. نظرهای بدون امتیاز در میانگین و نمودار شمرده نمی‌شوند. |
| `orderNumber` / `orderVerified` | شمارهٔ سفارش اختیاری؛ پرچم «خرید تأییدشده» فقط از تطابق با یک سفارش واقعی (`orders` یا `chat_orders`) ست می‌شود و در پاسخ‌های عمومی نمایش داده نمی‌شود. |
| `authorPhone` | شمارهٔ تماس **اختیاری** که مشتری در فرم نظر می‌نویسد (همان شمارهٔ باشگاه مشتریان). سرور آن را نرمال می‌کند (ارقام فارسی → لاتین، حذف جداکننده‌ها) و فقط داخل پنل نشان می‌دهد؛ در هیچ پاسخ عمومی برنمی‌گردد. اگر با عضو باشگاه مطابقت داشته باشد، امتیازِ نظر به همان عضو تعلق می‌گیرد. |
| `status` | `PENDING` (پیش‌فرض)، `APPROVED`، `REJECTED`. |
| `featured` / `featuredOrder` | «نمایش در Table Talk صفحهٔ اصلی» و ترتیب دستی آن. |
| `images` | تا ۴ تصویر پیوست (فهرست عمومی سقف می‌زند). |
| `replyBody` / `replyAt` | پاسخ رستوران که زیر نظر در صفحهٔ محصول دیده می‌شود. |

اعمال روی دیتابیس: `prisma/upgrades/20261017-customer-reviews.sql` (idempotent،
بدون عملیات مخرب). روی محیط‌هایی که با `prisma db push` ساخته می‌شوند، همان
`schema.prisma` کافی است.

## ۳. قرارداد API

### عمومی (بدون توکن)

| متد | مسیر | پاسخ |
| --- | --- | --- |
| `GET` | `/api/public/testimonials?limit=12` | `{ items: [{ id, authorName, authorNameEn, body, bodyEn, rating, orderVerified, createdAt, productName }], total }` |
| `GET` | `/api/public/reviews?productId&page&pageSize&sort&rating&withImages` | `{ items, summary: { average, total, distribution }, total, page, hasMore }` |
| `POST` | `/api/public/reviews` | بدنه: `{ productId, authorName, rating, body, orderNumber?, authorPhone? }` → `201 { review: { id, status: "PENDING" } }` |

- `sort`: `newest` \| `oldest` \| `highest` \| `lowest` — `withImages`: `0/1` یا `true/false`.
- در فهرست عمومی صفحهٔ محصول، `summary` **کل** محصول است (مستقل از فیلترها) و
  `total` فقط نظرهای منطبق با فیلتر.
- `POST` عمداً برای محصول نامعتبر **۴۰۰** می‌دهد و نه ۴۰۴؛ چون کلاینت وب‌سایت هر
  ۴۰۴ روی این مسیر را «مسیر ساخته نشده» تفسیر می‌کند و بی‌صدا به دادهٔ آزمایشی
  می‌رود.
- ثبت نظر با نرخ‌محدودی جداگانه محافظت می‌شود (`reviewSubmitLimiter`: ۵ درخواست در
  ساعت برای هر IP).
- `authorPhone` اختیاری است؛ وقتی ارسال شود باید با همان الگوی تلفن مشترک وب‌سایت
  (`src/utils/phone.ts`) بخواند (مثل `۰۹۱۲ ۳۴۵ ۶۷۸۹`) وگرنه ۴۰۰ می‌گیرد. سرور آن را
  به لاتینِ بدون جداکننده (`09123456789`) تبدیل و ذخیره می‌کند و در پاسخ‌های عمومی —
  چه فهرست صفحهٔ محصول و چه فید Table Talk — هرگز برنمی‌گرداند.
- **امتیاز باشگاه:** اگر مشتری عضو باشگاه باشد و شمارهٔ تماس را بنویسد، فرم
  وب‌سایت بلافاصله ۵۰ امتیاز (`POINTS_PER_REVIEW` در `src/utils/loyalty.ts`) به
  همان عضو می‌دهد و در پیام موفقیت نشان می‌دهد. هر نظر فقط یک بار امتیاز می‌دهد
  (dedupe با `reviewRewards` بر اساس `reviewId`) و مهمان‌ها یا شماره‌های ناشناس
  امتیازی نمی‌گیرند.

### پنل ادمین (پشت `requireAuth`)

| متد | مسیر | توضیح |
| --- | --- | --- |
| `GET` | `/api/reviews?page&pageSize&search&status&featured` | `{ items, pagination }` — ردیف کامل پنل: `orderNumber`، `authorPhone`، متن، تاریخ واقعی (`createdAt`) و همهٔ وضعیت‌ها. `search` در نام، متن و شمارهٔ تماس جستجو می‌کند و با ارقام فارسی هم شمارهٔ ذخیره‌شدهٔ لاتین را پیدا می‌کند. |
| `PATCH` | `/api/reviews/:id` | `{ status?, featured?, featuredOrder?, replyBody?, authorName?, authorNameEn?, body?, bodyEn?, rating?, authorPhone? }` — بدنهٔ خالی ۴۰۰. شمارهٔ تماس اصلاح‌شده هم نرمال ذخیره می‌شود. |
| `DELETE` | `/api/reviews/:id` | حذف کامل (۲۰۴). |

> شمارهٔ تماس، شمارهٔ سفارش و متن کامل نظر **دادهٔ داخلی پنل** هستند؛ فقط همین مسیر
> آن‌ها را برمی‌گرداند. ستون «شمارهٔ تماس» در جدول `/comments` برای مقدار خالی
> «ثبت نشده» نشان می‌دهد.

### آمار داشبورد و زنگ اعلان‌ها

`GET /api/dashboard` علاوه بر بقیهٔ شمارنده‌ها `stats.pendingReviews` (تعداد
نظرهای `PENDING`) را برمی‌گرداند. زنگ نوار بالای پنل (`TopBar/Notification`) از
همین عدد استفاده می‌کند و کنار تیکت‌های در انتظار و سفارش‌های امروز، «نظرهای در
انتظار تأیید» را هم نشان می‌دهد؛ بعد از تأیید/رد هر نظر، کش `["dashboard"]`
دوباره پر می‌شود و عدد همان‌جا به‌روز می‌شود.


## ۴. چطور یک روایت به صفحهٔ اصلی می‌رسد؟

1. مشتری در صفحهٔ محصول نظر می‌نویسد → رکورد با وضعیت `PENDING` ذخیره می‌شود
   (فقط با شناسهٔ محصولی که در دیتابیس فعال است). فیلد اختیاری «شمارهٔ تماس» برای
   اعضای باشگاه از پیش با شمارهٔ خودشان پر می‌شود؛ اگر شماره به عضویت موجود بخورد،
   امتیاز نظر (۵۰) بلافاصله به همان عضو داده می‌شود.
2. مدیر در پنل → **نظرهای مشتریان** (`/comments`) نظر را **تأیید** می‌کند
   (`status: APPROVED`). از این لحظه نظر در صفحهٔ محصول دیده می‌شود. نظرهای در
   انتظار تأیید در زنگ اعلان‌های نوار بالا هم شمرده می‌شوند (`stats.pendingReviews`).
3. مدیر کلید **«نمایش در Table Talk صفحهٔ اصلی»** را روشن می‌کند
   (`featured: true`). کلید همیشه قابل استفاده است؛ اگر برای نظری در انتظار تأیید
   روشن شود، در همان یک درخواست نظر را هم تأیید می‌کند
   (`PATCH { featured: true, status: "APPROVED" }`).
4. صفحهٔ اصلی از `/api/public/testimonials` می‌خواند و همان روایت‌ها را نشان
   می‌دهد؛ ترتیب اول با `featuredOrder` و بعد تازه‌ترین‌ها.

> فقط نظرهای `APPROVED` **و** `featured` به صفحهٔ اصلی می‌روند. نه رأی خودکار، نه
> چرخش تصادفی و نه دادهٔ ساختگی.

## ۵. وضعیت‌های رابط کاربری بخش Table Talk

| وضعیت | نمایش |
| --- | --- |
| در حال بارگذاری | اسکلت سه‌خطی (`aria-busy`) در همان قالب کارت؛ بدون پرش چیدمان. |
| داده دارد | نقل‌قول درشت + نام + امتیاز (اگر ثبت شده) + نشان «خرید تأییدشده» (اگر تأیید شده) + نام محصول + تاریخ + شمارنده و کنترل قبلی/بعدی. |
| فهرست خالی | **کل بخش پنهان می‌شود** (هیچ بلوک خالی و هیچ متن جایگزینی روی صفحه نمی‌آید). |
| خطای شبکه/سرور | پیام کوتاه «روایت مهمان‌ها همین حالا در دسترس نیست» + دکمهٔ «تلاش دوباره». |

`status: "error"` کش نمی‌شود؛ «تلاش دوباره» واقعاً درخواست تازه می‌زند
(`refreshTableTalk`). پاسخ موفق کش می‌شود تا بازگشت به صفحهٔ اصلی درخواست تکراری
نزند.

## ۶. دسترس‌پذیری، حرکت و موبایل

- کارت اسلایدر `role="group"` با `aria-roledescription` است، نقل‌قول در یک ناحیهٔ
  `aria-live="polite"` قرار دارد و دکمه‌ها `aria-label` فارسی/انگلیسی دارند.
- کلیدهای `→`/`←` با جهت صفحه هم‌راستا می‌شوند (در RTL برعکس)، `Home`/`End` هم
  کار می‌کنند.
- هیچ حرکت خودکار (autoplay) وجود ندارد؛ انیمیشن جابه‌جایی ۰٫۳ ثانیه است و با
  `prefers-reduced-motion` کامل خاموش می‌شود (`prefersReducedMotion()` و قاعدهٔ
  سراسری CSS).
- چیدمان دو ستونی در `lg` و تک‌ستونی در موبایل؛ تایپوگرافی با `clamp` مقیاس
  می‌گیرد و شکست خطوط با `text-balance` متعادل می‌شود.
- متن‌ها همیشه به‌صورت متن ساده رندر می‌شوند (بدون `dangerouslySetInnerHTML`).

## ۷. دستورها و تست‌ها

```bash
# وب‌سایت
cd website
npx tsc --noEmit                 # بررسی نوع‌ها
npm run test:tabletalk           # تست واحد منطق Table Talk (node --test)
npm run test:tabletalk:e2e       # ساخت + بررسی رندر در کروم هدلس (فید واقعی)
$env:SMOKE_TABLETALK='empty'; npm run test:tabletalk:e2e   # حالت فهرست خالی
$env:SMOKE_TABLETALK='error'; npm run test:tabletalk:e2e   # حالت خطا
$env:SMOKE_TABLETALK='fa';    npm run test:tabletalk:e2e   # کلیک روی تغییر زبان → رندر RTL فارسی
npm run test:reviews             # تست واحد نظرات صفحهٔ محصول
npm run test:reviews:e2e         # بررسی رندر بخش نظرات محصول
$env:SMOKE_REVIEWS='json'; node tests/reviews.e2e.mjs     # حالت دادهٔ واقعی API (بدون بنر دادهٔ آزمایشی)

# بک‌اند
cd dashboard/backend
npm test                         # API روی اسکیمای ایزولهٔ واقعی Postgres
node prisma/seed.js              # محصولات + روایت‌های منتقل‌شدهٔ Table Talk

# پنل
cd dashboard/frontend
npm test                         # تست واحد نرمال‌سازی‌ها
npm run build                    # ساخت پنل
npm run quality                  # بررسی‌های امنیتی/ساختاری
```

## ۸. یادداشت‌های مهاجرت

- سه روایت قبلی که به‌صورت متن ثابت در `src/data/content.ts` بودند، در
  `prisma/seed.js` (بلوک `tableTalk`) به دیتابیس منتقل شده‌اند تا از پنل قابل
  ویرایش/حذف باشند. این آرایه از `content.ts` حذف شده است؛ منبع حقیقت فقط
  دیتابیس است.
- آن سه روایت **بدون امتیاز** ثبت شده‌اند، چون امتیاز واقعی نداشتند؛ برای همین
  ستاره‌ها در کارت Table Talk فقط وقتی دیده می‌شوند که امتیاز ثبت شده باشد.
- صفحهٔ قبلی پنل («نظرات») در واقع نظرهای **تیکت‌های پشتیبانی** را با امتیاز و
  وضعیت ساختگی نشان می‌داد؛ حالا همان مسیر (`/comments`) به جدول واقعی `reviews`
  وصل است. API تیکت‌ها (`/api/comments`) دست‌نخورده باقی مانده است.
- ستون `authorPhone` بعداً به مدل اضافه شد؛ روی دیتابیس‌های موجود با
  `ALTER TABLE "reviews" ADD COLUMN IF NOT EXISTS "authorPhone" TEXT;` در همان فایل
  ارتقا اضافه می‌شود. ردیف‌های قدیمی `NULL` می‌مانند و پنل برای آن‌ها «ثبت نشده»
  نشان می‌دهد؛ هیچ دادهٔ قبلی تغییر نمی‌کند.
- باگ پنل «ستون‌های خالی نظرها» از این بود که `useReviews` پاسخ خام API را
  برمی‌گرداند و `normalizeReview` روی آن اجرا نمی‌شد (برخلاف `useProducts` و
  `useTickets`). حالا همهٔ ردیف‌ها از همان نرمال‌ساز عبور می‌کنند و به همین دلیل
  سوئیچ «نمایش در Table Talk» هم دیگر قفل نمی‌ماند.
